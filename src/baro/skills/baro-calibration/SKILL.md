# baro-calibration

baro の残り時間は「見込み × 補正の倍率 − 経過」で出す。倍率は手順の **テーマ** ごとに、この PC の履歴から毎回その場で計算する。
このスキルを使わなくても補正は効く。組み込みのテーマ分けがあり、`baro end` のたびに calibration.json も作り直されるため。
このスキルの仕事は、テーマ分けそのものをこの PC の仕事の癖に合わせて直し、精度をもう一段上げること。

## 仕組み（直す前に知っておくこと）

- テーマ分けは `calibration.json` の `themes`（無ければ組み込みの値）。先頭から順に見て、手順の名前にキーワードを 1 つでも含む最初のテーマになる。どれにも入らなければ `other`。**順番が大事**（「README を書く」を文書に入れたいなら、文書を「作る」より前に置く）。
- 倍率は 3 段で寄せる。履歴全体 → テーマ → その計画の中の実績。どの段も「見込み何分ぶんの仮の値を混ぜるか」の重み（`weights`）を持つ。記録が少ないうちは上の段の値に近い。
- `baro calibrate` は特徴データ（`features`）を作る。続けて、過去の手順を 1 つずつ、それより前の記録だけで予測したときのずれ（`backtest`）を、補正なし・全体の補正だけ・テーマ別で比べる。ずれの小さいほうを `mode` にし、記録が 20 手順以上あれば重みも選び直す。
- ずれ（`error`）は |log(予測/実績)| の平均を倍に直した値。1.00 で完全に当たり、2.00 なら平均で 2 倍外れている。`within_1_5x` は 1.5 倍以内に収まった割合。
- `history.jsonl` は直さない・消さない（記録そのもの）。直してよいのは `themes` だけ。

## 手順

### 1. いまの状態を見る

```bash
baro calibrate --dry-run          # テーマごとの見込みと実績・ずれ・重み（書き込まない）
baro calibrate --list --dry-run   # 手順ごとに、どのテーマに入ったか（タブ区切り: テーマ・見込み・実績・倍率・計画・手順）
```

記録が 10 手順未満なら、テーマを直しても比べられない。その旨を伝えて終える。

### 2. 直す候補を探す

`--list` の出力を読み、次を探す。

- **入れ違い**: 名前の意味と違うテーマに入っている手順（例: 「回答待ちが解ける不具合を直す」が「回答」で人の確認に入る）。キーワードが広すぎる・順番が悪いのが原因。
- **どれにも入らない**（`other`）手順: 共通する言い回しがあればキーワードに足す。
- **中身が混ざったテーマ**: 実績÷見込みの 25〜75% の幅が広い、または 1 件だけ大きく外れたものがある。性質の違う仕事が同じテーマに入っている（例: 「コードを調べる」と「VM・Docker・本番の状態を調べる」）。分けると当たることがある。
- **人や外の待ち**: 人の確認・CI・デプロイ・ビルドの待ちは、見込みとの比が他と大きく違いやすい。独立したテーマにしておく。

### 3. 候補のテーマ分けを書いて比べる

いまのテーマ分けを書き出し、直した候補を作業用のフォルダに置く。

```bash
work=$(mktemp -d)
baro calibrate --json --dry-run > "$work/now.json"
python3 -c "import json,sys; print(json.dumps({'themes': json.load(open(sys.argv[1]))['themes']}, ensure_ascii=False, indent=1))" "$work/now.json" > "$work/themes.json"
# $work/themes.json を Edit で直す（キーワードの追加・削除、順番の入れ替え、テーマの追加・分割）
baro calibrate --themes "$work/themes.json" --dry-run --list   # 入れ違いが直ったか
baro calibrate --themes "$work/themes.json" --dry-run          # ずれが小さくなったか
```

テーマは `{"key": "英小文字", "label": "日本語の名前", "keywords": ["…", …]}` の形。`key` の `other` は使わない。

比べる値は `テーマ別 ×…`（`backtest.theme.error`）。直す前の値と並べて記録しておく。

### 4. 採用するかを決める

次をすべて満たすときだけ採用する。満たさなければ、直す前のテーマ分けのままにする。

- テーマ別のずれが、直す前より **3% 以上** 小さい。
- 新しく作った・分けたテーマに、記録が **3 手順以上** ある（1〜2 件に合わせたテーマは、たまたまの当たりになりやすい）。
- キーワードは仕事の種類を表す一般的な言葉にする。プロジェクト名・人名・その回だけの固有名詞（`keiyukai`・`eta-band.zip` など）は入れない。入れると次からの手順に効かない。

採用するなら書き込む。

```bash
baro calibrate --themes "$work/themes.json"
```

以後は `baro end` のたびに、このテーマ分けのまま特徴データと重みだけが作り直される。組み込みのテーマ分けに戻すなら `baro calibrate --reset`。

### 5. 報告する

短く次を伝える。

- 記録の数（手順・計画）
- 直したこと（どのキーワード・順番・テーマを、なぜ）
- ずれ: 直す前 → 直した後（テーマ別・全体の補正だけ・補正なし）
- 採用したか、しなかったか（しなかったなら理由）
- 見込みの付け方への助言が読み取れたら 1〜2 行（例: 「git・PR は見込みの 0.1 倍で終わっている。見込みを小さく付けてよい」）

## してはいけないこと

- `history.jsonl` の書き換え・削除。
- 比べずにテーマ分けを書き込むこと（必ず `--dry-run` で直す前と直した後のずれを比べてから）。
- `weights` を手で書くこと（`baro calibrate` が過去の記録で選ぶ）。
- 補正の倍率を、作業中の進捗表示や返信で利用者に見せること（残り時間と終わる時刻だけを見せる）。
